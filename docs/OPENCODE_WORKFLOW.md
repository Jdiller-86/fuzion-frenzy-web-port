# OpenCode model routing and development workflow

The continuous target and local five-minute scheduled cycle are in [the OpenCode goal](OPENCODE_GOAL.md).

This repository uses [the project OpenCode V2 configuration](../.opencode/opencode.jsonc). It leaves the working global OpenCode Go, OpenAI OAuth, Unsloth and REA connections intact. OpenCode 2.2.5 discovers the project config when started in this repository. A fresh session defaults to `builder` with `opencode-go/deepseek-v4.1-flash`; existing sessions retain their own selected agent and model until changed explicitly.

| Agent | Provider/model | Use | Tool boundary |
| --- | --- | --- | --- |
| `builder` | `opencode-go/deepseek-v4.1-flash` | Bounded implementation, tests, task coordination | May edit source and delegate to `scout`, `reviewer` or `architect`; no REA |

## Unified two-session orchestration

The streamlined flow keeps exactly two persistent main sessions: the pinned hourly architect session (`.worktrees\opencode-architect-cycle-session.txt`) and one constantly running pinned manager session (`.worktrees\opencode-manager-cycle-session.txt`). The manager spawns and manages the three builder lanes; each lane keeps its own pinned builder sub-session started on demand.

- **In-OpenCode heartbeat:** `.opencode/plugins/orchestrator/index.ts` loads in the shared OpenCode background service for the architect worktree project only (directory guard). It keeps the pinned manager session, prompts it only when a lane is idle, a lane finished, an assigned lane failed to start, or fresh approved architect goals exist, records the same `MANAGER_*` lane cards to `.worktrees\opencode-manager-guidance.json`, starts lane tasks with `Start-ScheduledTask`, and writes `.worktrees\opencode-manager-heartbeat.json` on every beat. It never edits tracked files, never touches GitHub, never invokes models directly and never overrides architect decisions.
- **Goals channel:** the hourly architect review still writes `.worktrees\opencode-architect-guidance.json`; the manager treats it as its goals and may not override holds or route decisions.
- **Watchdog ladder:** `tools/Invoke-OpenCodeManager.ps1` stays registered (PT15M) as a cheap probe - it exits without any model call while the plugin heartbeat is fresh (under 12 minutes) and otherwise runs the same pinned manager session, cards and lane starts; `-Force` skips the freshness check for recovery. The hourly `tools/Invoke-OpenCodeArchitect.ps1` ends with a watchdog that recovers a stale manager heartbeat directly and records the outcome in its cycle state.
- **Application record:** the user explicitly authorized the hourly architect to apply this package directly (2026-11-04), so it was committed on `codex/opencode-architect` by the architect session instead of being imported by the primary lane; the next hourly review still verifies it before publication.
- **Architect model (W013):** GLM-5.3 is the permanent hourly architect model with glm-5.3-flash-free as the availability fallback; no automated path spends Sol. The user brings Sol in manually by explicit invocation only, for example `opencode run --auto --agent architect_fallback --model openai/gpt-6.1-sol` in the architect worktree.
- **Rollout:** per-lane periodic triggers are disabled once the orchestrator is live; the lane tasks stay registered for on-demand starts, and the Architect plus Manager tasks remain permanently as the watchdog ladder. Model routing, lane ownership, source-only publication, exact-head PR markers and every evidence gate are unchanged; this is workflow tooling, not original-game execution or playability evidence.

## Current three-lane scheduler

The source lane uses Go DeepSeek V4.1 Flash, the geometry lane uses Go MiMo V2.6 Flash, and the verification lane uses Go MiniMax M3.1 Flash. These are three different model families and separate Git worktrees. Geometry runs only when a current architect/manager task has actionable reference evidence. Verification owns only source-owned integration/check tooling, matching tests, and `docs/INTEGRATION_VERIFICATION_CHECKPOINT.md`; the runner rejects publication if that lane commits another path. Each lane has a separate lock and model fallback list in [`tools/opencode-builder-models.json`](../tools/opencode-builder-models.json). The same underlying model family is never a primary model in two builder lanes. Temporary free variants may exhaust their allowance; the runner moves to the next configured cheap model only after a recognized model/allowance error.

`FuzionFrenzy-OpenCode-Manager` runs a read-only GLM-5.3-Flash manager every 15 minutes. It writes bounded `RUN` or `HOLD` task cards to ignored `.worktrees/opencode-manager-guidance.json`; exact branch heads and a two-hour age limit prevent stale tasks from directing a builder. The manager cannot edit source, publish, approve designs, or merge. The hourly `FuzionFrenzy-OpenCode-Architect` remains the authority for design, reviewed integration and PR decisions, using linked Sol first and full Go GLM-5.3 during Sol's cooldown. The verification builder has its own 15-minute task and Desktop-visible worktree; the existing five-minute source and hourly geometry schedules remain. The manager can hold a lane without pausing the overall project. Local Qwen remains a read-only Scout. Older two-lane/free-geometry descriptions below record prior policy and do not override this section.

Project policy allows only `builder`, `scout`, `reviewer` and `architect` child agents. The builder may call Sol without a separate user approval when the escalation rules below apply; a subagent cannot delegate again at the default depth limit. Its OpenAI provider is the active linked ChatGPT/Codex OAuth method (`chatgpt-token-sharing`), not an API key. To start with Sol as the primary architect, select both `architect` and `openai/gpt-6.1-sol` in a new Desktop session. Selecting a primary agent alone does **not** switch an existing session's model. On the CLI, use `opencode run --agent architect --model openai/gpt-6.1-sol "<architecture question>"`. The default CLI run uses DeepSeek Go. Never substitute `opencode/deepseek-v4.1-flash` or `opencode/gpt-6.1-sol`: those are different provider routes.

## One bounded task

1. Read `AGENTS.md`, the current handoff/status, the relevant checkpoint and the affected source. Capture a task card with a concrete result, files in scope, acceptance checks, evidence boundary and unresolved questions.
2. Delegate a narrow read-only source search to local `scout` with exact paths and a short answer limit. The project override gives Qwen a 32,768-token context; direct OpenCode source reads passed in both private and shared-service runs. Treat Scout output as a lead and verify material findings. Direct Ghidra remains the XBE route documented in `ANALYSIS_SETUP.md`; REA's Windows XBE admission is not assumed.
3. Use `builder` for the smallest coherent implementation. For CPU instruction semantics, memory accounting, ABI, GPU compatibility or an unresolved correctness defect, obtain an independent `reviewer` finding against actual changed code and tests. A review is evidence to inspect, not a substitute for executing the original title.
4. Escalate automatically to `architect` when a decision changes the project route or multiple subsystems, two targeted attempts fail, or a GLM review leaves a material CPU, memory, ABI or GPU correctness question unresolved. Send: objective; observed behavior; exact evidence/checks; attempts; remaining hypotheses; decision needed. Use one bounded Sol call per decision; return implementation to DeepSeek. Stop and report if that call cannot resolve the decision.
5. Finish with changed files, checks actually run, observed original-runtime behavior, remaining gaps and next task. Update `PROJECT_STATUS.md`; record consequential choices in `DECISIONS.md`. Do not claim a playable game from translated-function counts or component fixtures.

Agent step caps (builder 48, scout 8, reviewer 12, architect 32 in its integration worktree) stop a single prompt sequence; a new user input resets the cap. They are usage brakes, not billing limits. Builder worktree policy blocks direct Git push/merge; architect worktree policy permits reviewed local merges but blocks direct push. The scheduled runner alone publishes checked architect commits. Project policies block environment-file reads/edits and external-directory tool access, but shell commands and plugin code are **not** contained by these project rules. Keep cloud-model work in source-only worktrees. Do not put original game files, converted assets, pseudocode, credentials or raw research logs in prompts, issues, PRs or model attachments. Local Qwen can analyze local evidence; send cloud models only curated findings.

## Source control and GitHub

Use a clean worktree from a reviewed source-only commit for cloud agents. The main checkout contains ignored `research/` and player-supplied game files, so a Git ignore rule alone is not an isolation boundary. The local `.worktrees/` directory is ignored. Keep one branch/task owner per worktree; use `codex/<task>` names. Do not copy ignored material into a worktree or access the main checkout's ignored game/research inputs from a cloud-agent shell. Follow the current handoff for the active runtime boundary.

Two scheduled lanes may work concurrently with separate OpenCode Desktop sessions and Git branches. The five-minute `opencode-source` lane owns original startup, runtime services, device/memory/FATX work, route decisions and the broad project status. The hourly `opencode-geometry` lane owns only source-owned `src/runtime/nv2a_*` components, their matching tests and `docs/NV2A_GEOMETRY_CHECKPOINT.md`. It works on an independent branch based on the last committed source-lane checkpoint; it must not modify the primary lane's files, claim original rendering from a fixture, or use ignored game/research inputs. Each lane has its own lock, state and session pin; at most one builder prompt per lane runs at once. The geometry lane uses only `opencode/deepseek-v4.1-flash-free`; it does not call Go, Sol or other-model subagents. A material correctness blocker is recorded for the primary lane. Review and integrate geometry changes into the original-execution lane separately when a concrete dependency is reached; do not automatically merge branches.

The hourly `FuzionFrenzy-OpenCode-Architect` task owns a persistent `codex/opencode-architect` integration worktree. Linked-account Sol compares both builder heads and local main, sets priorities for both lanes, approves consequential design decisions in `docs/DECISIONS.md`, updates governing docs, and should first delegate one useful narrow source lookup or commit classification to local Qwen Scout. It verifies material Scout findings; Scout failure cannot pause the review. Sol can inspect and merge reviewed committed branches into its own integration branch; it cannot rewrite or discard uncommitted builder work. Every cycle it receives an open-PR snapshot and decides whether committed source/geometry work merits a draft review PR into integration or whether the integration head merits a PR into main. Sol explicitly requests a new PR with `OPEN_SOURCE_REVIEW_PR: <exact source HEAD>`, `OPEN_GEOMETRY_REVIEW_PR: <exact geometry HEAD>`, or `OPEN_MAIN_PR: <exact integration HEAD>`; absence of a marker means no PR creation. After a clean checked Sol cycle, the runner publishes the integration branch and executes only those exact requests through GitHub's API using the cached Git credential, with no token in source or logs. Sol can request `MERGE_MAIN_PR: <exact HEAD>` only after reviewing that integration head. The runner then requires clean source-only history, `npm run check`, `npm run test:runtime`, whitespace checks, local/remote main ancestry, both successful GitHub preparation jobs, current PR head/base and clean mergeability before using GitHub's merge-commit API. Pending checks or conflicts defer the merge; no direct push to main or protection bypass occurs. Other open main PRs are shown to Sol for review but are not auto-merged. A Sol allowance failure yields provisional read-only free GLM Flash advice without decision, merge or promotion authority.

Use a scoped branch/worktree, targeted tests and source-only review for each bounded change. The public GitHub repository and source-only CI already exist. `gh` is not installed; `tools/Invoke-OpenCodeGitHubPR.ps1` uses the cached Git Credential Manager credential in memory for GitHub PR metadata, architect-requested creation and guarded merge. Do not assume GitHub Actions can access localhost Unsloth, desktop OAuth or REA. Before staging, run `npm run check`, inspect the staged paths and `git diff --cached --stat`, and keep all original content and credentials out of Git history. The Windows cycle runner publishes verified commits to each lane's `origin/codex/opencode-*` branch after each successful cycle. The architect runner publishes its reviewed integration branch and maintains at most one PR per requested lane/base pair and one integration PR into main; it may merge only its own exact approved architect main PR after the gates above. PR and publication failures are recorded for later retry; no force push is permitted.

## Quick CLI checks

Run from the repository or its clean worktree:

```powershell
opencode debug config
opencode debug agents
opencode models
opencode auth list
opencode mcp list
```

`debug config` should include `.opencode/opencode.jsonc`. `debug agents` should show the configured roles including manager and their exact provider IDs. `auth list` shows credential presence only; it does not prove a live model request. `mcp list` should report `rea` connected. A live smoke test is separate from these configuration checks and consumes the selected provider's allowance.

## Active architect steering

Each hourly architect review compares builder commits with its prior directive, assigns a bounded next result and acceptance check to each active lane, and redirects drift or repeated low-value work. It reviews the current main PR head independently of unmerged builder branches and seeks a safe, reviewed source slice for integration rather than waiting for an entire growing branch. A clean approved `GEOMETRY_CYCLE: HOLD` directive defers the geometry lane's scheduled model prompt when no actionable reference exists; `GEOMETRY_CYCLE: RUN` resumes it. The primary builder and overall goal continue during a geometry hold. Existing source, runtime, CI and merge gates still apply.

## Architect usage fallback and public status

When linked-account Sol reaches a usage limit, the hourly runner uses the project `architect_fallback` agent on full OpenCode Go GLM-5.3 with a 20-step cap. This fallback may direct builders and approve bounded, source-only integration or an exact-head PR merge through the same checks, but may not change the original-game route or local-content requirement. Sol is probed again after a six-hour cooldown. If full GLM also reaches its allowance, a free-model review is provisional and cannot approve or merge; the GLM-5.3-Flash manager and independent builders continue within prior approved bounds. The runner refreshes [GitHub development status issue #4](https://github.com/Jdiller-86/fuzion-frenzy-web-port/issues/4) after each architect cycle, including failed model cycles, using only source-owned branch metadata and the current checkpoint title. The issue does not establish playability.
The fallback receives a shorter hourly prompt to limit usage. If it completes tools without a final directive, the runner asks once for a tool-free conclusion; PR actions require a clean cycle and an explicit `ARCHITECT_REVIEW` marker. The issue is a progress page; GitHub may not notify watchers when its body is edited.

The architect runner now captures `$fullResponse = $response` before the 1800-character `lastSummary` truncation and matches `ARCHITECT_REVIEW`, `GEOMETRY_CYCLE`, `OPEN_MAIN_PR`, `OPEN_SOURCE_REVIEW_PR`, `OPEN_GEOMETRY_REVIEW_PR` and `MERGE_MAIN_PR` against the full response. `lastSummary` and the 1200-character summary cap are unchanged; this fixes the silent loss of PR markers that fell outside the trailing window. The PowerShell AST parse reports 0 errors.
After each completed architect cycle, the status publisher also posts one concise comment to that issue. It deduplicates by architect-cycle finish time and includes only public branch metadata, cycle outcomes, the current source checkpoint title, and the main PR link. To receive these by email, the GitHub account must have the desired address verified and select it for email notifications, including own issue updates. The runner holds no mail credentials. Issue replies are not yet read by the scheduled architect, so a reply alone does not change its task. Do not include private research or game content in status comments.
