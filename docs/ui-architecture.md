# Original UI architecture: source-backed checkpoint

This note records a bounded read of the pinned retail XBE, selected archived resources, and local desktop captures of the original title running in the retained native host. It is not evidence of original-game execution in a browser. It separates facts visible in the original program from screen labels inferred from captures. Generated function labels such as `sub_0001CAB3` are analyst labels, not recovered Xbox symbols.

## What the evidence supports

The title owns its menu and in-game presentation. The original XBE has separate code paths for the main menu and Options mode. Each passes a screen-layout resource name to the same resource loader; the loader resolves the resource type and dispatches to the resource service. Exact resource-name addresses join to `Generic.xbp` entries, and bounded decoding of those overlays recovers isolated leaf views. Those views include uniquely hash-matched full-texture quads for a gradient asset, but omit parent transforms and do not identify which leaf draws a particular label or menu row. This supports the mode-to-resource link without establishing the complete mode registry or lifecycle.

The shared loader is `0x0004BB30`; the main-menu path pushes the resource-name pointer at guest address `0x0001CAD1` and calls the loader at `0x0001CAD8`. The Options path pushes its pointer at `0x0001D755` and calls the loader at `0x0001D75C`. The generated code then calls the title's resource service and stores returned objects in title-owned state. The Options block appears twice in generated shards at the same guest addresses, so generated analyst-label attribution is ambiguous.

The embedded main-menu and Options vtable pointers each reference 14 four-byte entries in XBE data. Seven same-index entries match across the two tables. Their event-handler candidates are each at slot 13: main menu `0x0001CB20`, Options `0x0001D790`. The main-menu handler accepts selector values 0–5; two branches move the per-object focus field at `+0xC4` forward/backward with wrap across four entries, while other cases dispatch additional mode actions. The Options handler accepts selector values 0–6; navigation updates a per-object field at `+0xCC` with a 0–5 wrap, and two value branches adjust per-object fields at `+0xB8` and `+0xBC` within 0–10 bounds. This is a code connection to menu state handling. The physical controller polling and the mapping from hardware inputs to these selector values are still unknown; the field meanings beyond their observed control-flow role are not assigned.

Each vtable's slot 7 also has a source-backed method entry. The main-menu entry `0x0001C400` continues into `0x0001C409`, which calls helpers `0x00030310` and `0x00043930` and then makes an indirect object call through offset `+0x0C`. Options entry `0x0001DD30` calls `0x00030310`, `0x00043B70`, `0x000438B0`, and `0x0001D060` twice, then makes an indirect object call through `+0x0C`. These connect each mode table to a presentation-oriented path, but helper identities, exact draw ordering, and per-layer semantics are not fully mapped. Slot 6 entries (`0x0001C470` and `0x0001CF90`) include global and floating-point checks and indirect calls through object offset `+0x08`; their broader lifecycle role remains unassigned.

A separate startup block passes the base string-table name through the same loader and stores the returned handle. The archive contains locale-suffixed string-table candidates. The exact locale-selection logic, string-ID mapping, and text renderer remain unverified.

The retained Windows renderer contains a separate, renderer-side clue about menu text: its 2D quad path derives a texture-coordinate rectangle from the draw's actual vertex buffer and insets the sample range by half a texel. Comments identify a 512×512 font-atlas menu case. This is host renderer behavior, not recovered title UI source; the atlas cell-to-character map and per-label string IDs remain unknown.

## Runtime observations

Fresh desktop captures show a blue-gradient title/menu presentation with a shared logo and a vertical menu. The focused row is bright while other rows are dimmed. The Options screen presents segmented sound and music controls, soundtrack/song selectors, vibration state, and change/back hints. In the recorded navigation path, left-stick input changed focus; the on-screen hint refers to D-pad input. In a live minigame, Start opens a translucent red panel over the paused arena; its menu includes continue, options, instructions, retirement, and quit. Entering the pause-panel Options opens the same sound/music controls.

Character-selection captures show six character portraits, left/right arrows, player join/confirm prompts, and a 3D character preview. The observed path uses A to confirm/advance, B to return, and left-stick right to change the selected character. A post-round capture shows a “play again” yes/no dialog with yes highlighted and player/CPU score widgets; the intermediate winner transition was missed. These are observations of this local run, not proof that every branch or controller behaves identically. No original keyboard mapping was established; keyboard support in the retained native host is a separate adapter.

Earlier retained rendering evidence records that the character-select screen's 2D artwork, text, and HUD rendered correctly while the skinned character mesh was broken. That independently supports a screen composed of UI and 3D content through the title's renderer. The pause capture visibly uses alpha blending over the arena. Exact blend factors, clipping rectangles, draw order between individual UI layers, and resolution-dependent layout rules have not been recovered.

## Coverage gaps and next probes

- Follow mode registration and transitions from the root/title state into main menu, Options, character selection, pause, and results. The captures establish some transitions, but no complete source-backed state graph is available.
- Trace the hardware controller poll-to-selector path and map the remaining mode methods. The event-selector state writes are traced, but input origin and left/right adjustment-to-render joins remain unknown.
- Trace the pause-panel source path and connect it to decoded texture resources. Pause corner/edge filename candidates have no exact XBE name and generated-literal match in the current scanner; this bounded no-hit does not prove they are unused.
- Trace string-table selection, string IDs used by the observed controls, font/glyph data, and text drawing. The current inventory does not decode the font data.
- Measure panel and list geometry, clipping, alpha blend state, animation timing, and draw ordering across the menu, character select, pause, and results screens.
- Connect the observed post-round play-again dialog and score widgets to a results-mode source path; the intermediate winner transition was not captured and the results source/resource join remains unproved.

This checkpoint does not establish complete original UI parity or accept a browser implementation. It excludes the native port's ImGui overlay and keyboard adapter: those are host-side tools, not the original game's UI.
