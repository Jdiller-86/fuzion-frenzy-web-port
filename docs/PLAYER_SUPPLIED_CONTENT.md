The user selected a player-supplied-game-files distribution model on October 31, 2026. This is the required product direction, not an assertion that all copyright, trademark, music, or reverse-engineering questions are resolved.

**Distribution boundary.** Publish independently written application/server code, importer/converter code, curated non-content findings, and appropriately licensed original placeholders. Do not distribute ROMs/disc images, original executables, textures, models, audio, animation, preconverted asset packs, decompiled game code, or game/firmware download links. Each connected browser supplies its own compatible game files. Local player seats in the same browser share that browser's local content context; this is a technical design, not a license determination.

The public repository and CDN contain no original game content. Required content cannot be supplied by another player, a match server, an account sync service, telemetry, or a crash report. The selected product route is static recompilation to WebAssembly; the historical asset-preview importer does not itself execute the original Xbox binary or establish the new runtime.

**Initial input target.** Prove the known uncompressed Xbox XISO `.iso` format first, using the locally supplied reference copy. Do not assume ordinary ISO9660 support reads XDVDFS. Additional disc layouts, loose-file directories, regional/modified builds and compressed `.7z`/`.zip` inputs require separate support decisions. The current 7z research archive is a developer reference input, not proof that browser archive import is implemented. Show users the actual supported format and a clear unsupported-build error; do not promise arbitrary ROM compatibility.

**Browser flow.** Provide Select game files -> identify supported build -> local conversion progress/cancel -> local asset validation -> controls/practice or lobby. Treat files as untrusted input. Check headers, ranges, dimensions, counts, decompression limits and filenames; never execute embedded code or follow paths outside the selected input. Reject malformed/truncated content without partially enabling play. Tests must include corrupt inputs built from source-owned fixtures.

Read the image with bounded random-access slices and process conversion in a worker. Do not read the entire approximately 2 GB reference image into an ArrayBuffer. Prove working-memory limits and responsiveness on the named desktop profile before committing to the full catalog. Start with a provisional 128 MiB importer working-memory budget excluding decoded active assets, and a first-activity import target of 120 seconds from the supported uncompressed image on the reference SSD profile. These are targets to measure, not observed results; change them through a recorded decision if the content requires it. Normal network shell-loading targets do not include the first local import.

**Local storage.** Conversion stays on the player's device. Offer optional local persistence with a visible size estimate, quota check and clear-delete control; support an explicit reselect/reimport fallback when persistence is denied or evicted. Key caches by build identity, converter version and content digest. Never silently upload bytes, filenames or derived assets to accounts, diagnostics, analytics, remote conversion, or external image-generation/upscaling services. In-browser/local visual enhancements must respect this boundary too.

**Multiplayer boundary.** Each connection completes its own import and compatible-content readiness checks. Send only the minimum supported-build/content identifiers, converter/rules versions, ready flags and gameplay protocol data needed for matching. Digests identify compatibility; they do not establish legal ownership or grant access to another user's content. No peer-to-peer ROM transfer or server-hosted asset fallback. Separate downloadable application modules from imported game data.

The authoritative server must run independently written rules and approved simulation geometry; it must not require players to upload their ROM or level assets. During feasibility work, determine whether collision/track/spawn data can be faithfully represented without redistributing proprietary level data. If not, record the conflict and resolve the architecture/distribution choice before promising that minigame. Do not silently put imported assets into a server image or repository as a workaround.

**Visual fidelity.** The user wants modernized assets that mirror or reuse the existing game assets where possible. Prefer locally imported original meshes, proportions, palettes, animation and audio as the fidelity baseline. Evaluate reversible rendering improvements such as resolution, filtering, lighting and optional effects. Preserve gameplay dimensions/camera readability; cosmetic mesh changes do not change hitboxes. Keep a faithful/reference presentation option for comparisons. Do not commission or substitute unrelated art merely because it is easier to implement, or ship locally converted originals on the public CDN.

**Release gate.** Before broad visual production, demonstrate local import -> one animated original character -> one representative arena -> one locally decoded audio cue in the actual browser, with no content upload and measured memory/time. If source formats or conversion fidelity remain unresolved, use clearly labeled placeholders for technical spikes and revise scope; do not claim the final content path is ready. The bounded one-profile research proof now demonstrates this path; see [G0/G1 audit](G0_G1_CHECKPOINT.md). It is not a production importer or complete conversion/fidelity acceptance.

Microsoft's fan-content rules restrict asset extraction through reverse engineering and impose conditions on branding and audio. The player-supplied model avoids our hosting the original files, but it is not a blanket permission conclusion. Keep independently written code provenance and remaining release questions explicit.
