The active implementation route is the matching Fuzion Frenzy recompilation SDK and game configuration, adapted to this project's checked browser runtime. The immediate result is the first original browser frame (MB17), or a runnable browser build failure with the exact adapter gaps and next implementation. Compilation, SDK coverage, or a desktop picture alone does not meet that result.

## Bounded desktop reference, then browser attempt

A native desktop reference is useful for a short diagnostic pass: verify and reuse a matching retained executable, or build it locally from the pinned source and the same private game input. It can expose a simple host-side baseline and clarify a visible frame or input behavior. It is not a product path, an M1 acceptance result, or a source of a convertible executable. Its kernel, VM, threads, files and renderer are native implementations; the browser attempt must compile the same C++ source and bridge those contracts explicitly.

Limit native-reference setup/build/run to the first **30 minutes** of the **150-minute initial local work-session decision budget**. Then attempt the browser build/run with that same source, configuration and local game input. The 30 minutes are a diagnostic allocation, not a deadline to finish the native port. If the retained executable is absent or the build is blocked, record the exact command, elapsed time and failure, then continue independent browser compilation and interface work. Do not wait for a complete native product.

At the 150-minute decision point, report wall time and active effort separately, including setup, build, browser execution, review and rework. Capture the first original browser frame if reached. Otherwise provide a runnable actual browser failure, the exact adapter-gap list and the next implementation. This is a decision checkpoint, not a guaranteed execution deadline or a validated weeks/months forecast.

## Fast iteration before M1

Keep the legacy M44 baseline, 512-function/64-binding caps, fixed memory limits and all existing guards intact. An experimental SDK module may define separate explicit memory/import/export/function/binding budgets, but validate them before execution and review them independently; do not silently relax inherited limits or checks. Choose the simplest supported worker, pthread or main-thread ownership arrangement. Do not require a novel cooperative pause/resume model. Batch supported shared-interface/provider fixes with focused checks and review instead of repeating full per-caller audits and handoffs.

Inspect retained toolchain/output/object caches before downloads or regeneration. [prepare-sdk-title.py](../tools/prepare-sdk-title.py) already validates the pinned local SDK/config/input and generates into a fresh ignored directory; [extend-recomp-batch.py](../translator/extend-recomp-batch.py) retains the legacy stop-driven preparation path. Reuse their manifests and the retained byte-preserving SDK block extractor instead of repeating one-off setup. The existing bulk inventory reports 10,589 static functions; it is not complete browser coverage. A compiler invocation or source-owned fixture alone does not establish a first original frame. Use the [iteration workflow](development-workflow.md) for purpose-specific private evidence and measured phase records.

Source-only private boundaries do not change: no game archives/images, XBE/firmware, generated title code, assets or raw proprietary evidence are committed, uploaded or distributed. The native-stage claims in upstream documentation remain upstream-reported until locally run. Detailed title fidelity and promotion of a milestone still require direct evidence. Preserve the existing conditional Goal A startup continuation, conditional Goal D legacy-capacity work, and the next ready Goal B graphics / Goal H audio work. Pins and provenance remain in the [toolchain manifest](../tools/original-execution-toolchain.json).
