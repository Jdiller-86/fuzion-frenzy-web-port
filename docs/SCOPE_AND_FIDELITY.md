This scope baseline was prepared before gameplay development, incorporating the user's October 31, 2026 decisions: a small online pack first, desktop keyboard/gamepad first, player-supplied game files, faithful original rules/game feel, and modernized visuals that mirror or reuse original assets where possible.

**Meaning of fidelity.** The goal is recognizable original gameplay with preserved scoring, objectives, movement response, collisions, hazards, camera readability and character/arena identity. Original menus, Xbox boot flow, exact rendering artifacts and frame-identical online execution are not first-release requirements. Modern browser menus, remapping, friends, accounts, lobbies and reconnection are intentional additions. Imported original content stays on the player's device; see `PLAYER_SUPPLIED_CONTENT.md`.

| Area | First public pack | Explicit boundary |
| --- | --- | --- |
| Content volume | Four to six selectable activities, counting the Frenzy objective round explicitly | Full catalog is a later milestone; do not count unseen variants as implemented games |
| Candidate mechanics | Proposed initial four activities: Twisted System, Sumo, Jetboat Sprint, and one Frenzy objective round | Names/rules need confirmation against the supplied build; a fifth/sixth activity is stretch scope after G4, not a commitment |
| Characters | Prototype: one imported character with distinct seat indicators; public-pack target: all six original characters through the local converter | Validate all six at G4; if conversion cannot meet this target, report the roster/schedule change before production rather than silently substituting |
| Arenas | The arenas needed for accepted pack activities, preserving relevant layout, scale and camera framing | All six zones and all their variants are full-game scope, not the first pack |
| Modes | Instructions/practice, single activities, custom playlist, shortened tournament with Frenzy scoring | Exact original two/four/six-stage content coverage requires the later full catalog |
| Players | One to four seats, offline local, online, mixed local/online, useful CPU fill | No increased player counts, ranked mode, or platform-service cross-play |
| Controls | Keyboard/gamepad semantic parity, remapping, analog calibration, clear prompts | Two shared-keyboard seats are conditional on rollover; touch/mobile later |
| Social/lobbies | In-app accounts/friends, privacy/blocking, invites/codes, ready/start, owner transfer, rematch and reconnect | No Xbox friends import, voice chat or unmoderated public text chat in the first pack |
| Bots | Functional per-minigame CPU controls with documented reaction/error behavior | Exact original hidden AI/difficulty equivalence is not assumed; label browser CPU settings accurately |
| Visuals | Locally imported originals as baseline; optional modern presentation preserving identity | No silently replaced character designs, gameplay geometry, or shipped original asset packs |
| Audio | Locally decoded cues/music where supported and synchronized as needed | No hosted original soundtrack; music/pattern games wait for the audio timing gate |
| Devices | Supported desktop Chrome, Edge, Firefox and Safari after real testing | No first-release phone/touch, arbitrary low-end hardware, or WebGPU-only dependency |

**Asset modernization rules.** Retain original silhouettes, proportions, key colors, arena landmarks, animation intent and readable hazards. Improve presentation through resolution/material/lighting/effect choices only after a reference comparison and performance measurement. Keep a faithful comparison preset. Do not replace original collision geometry with an enhanced visual mesh, or add effects that obscure timing/targets. Any new authored replacement needs provenance and a documented visual reference; do not copy a third-party fan remake or upload imported originals to an external enhancement service.

**Authoritative gameplay and online differences.** Offline play is the primary fidelity baseline. Online rounds use server outcomes and local prediction; network delay can change presentation/correction behavior. Preserve the rules and explicitly document the timing/fairness policy instead of promising original couch play frame for frame over the Internet. Avoid arbitrary client backdating. Fixups for latency, accessibility or altered gameplay belong in an identified shared ruleset, not hidden per-player advantages.

**Reference/test contract.** Each accepted activity needs a specification linked to a verified build and observed scenarios: instruction/control meanings, start/end conditions, score/ties, motion, collisions, hazards, power-ups, camera, team variants if relevant, audio cues and bot assumptions. The current entry-point decompilation establishes none of these numerical mechanics. A filename or string alone is not runtime evidence.

Freeze a reference scenario set and tolerances before implementing that activity. Starting tolerances are proposals: exact scoring/state-transition outcomes for equivalent inputs; action/hazard boundaries within one measured reference frame where reproducible; acceleration, turn/boost and knockback durations within 5% of measured reference values; collision boundaries compared in normalized world/character units. Use a tighter or different documented tolerance if a narrow window changes outcomes. Do not claim these provisional tolerances are already validated or that all source behaviors are deterministic. Human review by players familiar with the original supplements numeric cases.

Choose and document actual hardware before performance sign-off. The proposed baseline is a 16 GB desktop/laptop with an Intel Iris Xe class integrated GPU and SSD, current desktop browser, 1080p UI with adjustable render scale. Also test Safari on an Apple Silicon Mac. Target 60 fps at an agreed quality and a usable 30 fps fallback. A tested matrix, not engine marketing, defines supported machines.

**Go/no-go gates.** Complete these in order; technical placeholder spikes may overlap, but broad content production cannot outrun unresolved reference and asset questions.

| Gate | Bounded work | Required evidence / decision |
| --- | --- | --- |
| G0: Reference and content identity | Identify supplied build, inventory actual content, establish hardware/emulator captures or identify exactly what is missing | Source-safe findings index, reference scenarios, proposed first-pack activities; no claims of faithful timing without captures |
| G1: Browser/local asset path | Prove supported XISO parsing and local conversion for one animated character, one arena and one audio cue | Working browser proof; original file digest unchanged; no ROM/assets uploaded; memory/import-time measurements; compatible-build/error handling |
| G2: Offline fidelity | Reconstruct one timing activity with one-to-four local seats and practice | Reference comparison/tolerance report, exact score/tie cases, input/focus/device checks; identify all approximations |
| G3: Network and representative mechanics | Four remote seats, two-local-plus-two-remote, then contact, steering and orb objectives | Agreement on results, no duplicate pickups/rewards, bounded corrections, fair timing at 150 ms RTT/30 ms jitter/1% loss, no browser-host authority |
| G4: Freeze first-pack production | Review G0-G3, conversion coverage and effort per activity/character | Exact four-to-six activity list, roster/arenas, remaining fidelity deviations, updated effort/budget; revise openly if conversion cannot meet target |
| G5: Public-pack readiness | Complete social/control/lobby flows, content readiness barriers, browser/performance and recovery tests | No original content in repository/CDN/server; import/readiness required per browser; tested supported matrix; clear partial-release label |
| G6: Full-game parity | Expand by verified mechanic families and content inventory | Every original inventory entry/required mode accounted for, complete original characters/zones, documented fidelity acceptance |

Do not allocate more than five engineering days to an alternative recompilation route without an actual controllable/rendered proof and an integration case. Do not spend months rewriting an emulator, importing every asset, or perfecting menu art before G1-G3. If a reference, format or fidelity question remains unresolved, state the failed gate and offer a concrete route/scope adjustment; do not treat elapsed effort as evidence of success.

**High-risk families.** Contact needs simultaneous collision/knockback tests; vehicles need analog versus keyboard behavior, boost/reset and track validation; orb games need contested ownership/stealing/banking and durable scores; music/pattern games need beat/cue windows, output latency and online fairness; projectiles/complex hazards require their own deterministic-state/prediction tests before that family ships. Passing the first timing activity does not validate these families. Their individual catalog expansion remains out of the first pack unless explicitly selected at G4.

**Browser/import consequences.** Large disc images cannot become whole-file memory buffers. Compressed input adds decompression and startup cost; first support is the proved uncompressed XISO, with additional formats separately scoped. Import time is separate from website download time. Storage may be denied/evicted; provide reselect/reimport and clear-local-content controls. Every online browser supplies compatible content; there is no server/peer ROM fallback. The server's faithful rules/geometry must not require redistributing proprietary level data; a conflict is an architecture gate, not permission to hide assets in an image.

**Delivery estimate confidence.** The earlier 20-31 week first-pack and 12-24+ month full-parity ranges assume two-to-three engineers, technical art and part-time QA. They are not a forecast for one model running alone. Model choice does not remove asset conversion, runtime reference, physical-controller/browser QA, operating cost or content production work. Re-estimate at G1 and G4 using measured effort, with runtime/import/asset risks listed separately. No paid hosting/auth service is provisioned by this scope.

**Ready now versus unresolved.** Release sequence, target devices, player/file ownership boundary, visual direction, architectural authority and gate definitions are decided. Actual original asset formats, reference timing, the first-pack roster/activity list, browser conversion performance and full-catalog effort are not established. Those are deliberately bounded preproduction deliverables, not facts to invent before development. Full-force catalog development begins after G4; technical research/prototypes are the next work.
